# Agent Note: 手机键盘的布局视口

Status: implemented

[English](2026-11-16-mobile-keyboard-layout-viewport.md) | 中文

## 问题

Web GUI 按布局视口确定自身尺寸（`html`、`body`、`#root` 都是 `height: 100%`），并把输入框作为 sticky 座位停在会话列的底部。只有浏览器为键盘缩小布局视口时，这个底部才会让开屏幕键盘。Chrome 108 把 Android 的默认行为改成了 `resizes-visual`：视觉视口缩小，布局视口保持原高度，于是输入框的草稿、控制行和发送按钮都被键盘盖住，而页面本身没有可滚动的溢出可供平移揭示。

## 决定

`apps/web/index.html` 在 viewport meta 中声明 `interactive-widget=resizes-content`。Android Chromium 因此在键盘弹出时缩小布局视口：外壳的 `height: 100%`、AppFrame 的列、会话滚动区和输入框的 sticky 底部都止于键盘上沿，抽屉、菜单、对话框等固定表面也按缩短后的视口布局，而不是落在键盘后面。

键盘只抬升输入框，别的都不动。Chat 把「输入框文字区域持有焦点时滚动区高度发生变化」视为一次键盘切换（`use-chat-viewport.ts` 的 `ViewportResize`）：视口把对话已确认的滚动位置恢复回去（按缩短后的范围夹取），`ChatReading.onResize` 也不做普通布局缩放时的贴底跟随。缩短后的滚动区于是在同样的屏幕位置绘制同样的内容，只有输入框的 sticky 底部随键盘上移。键盘还在时也会继续改变滚动区高度（候选栏出现或消失），这些变化同样保持不动，直到滚动区回到键盘弹出前的初始高度或文字区域失焦。内容增长不是键盘切换，流式输出仍然跟随底部。

## Alternatives considered

- **在外壳里跟随视觉视口。** 由外壳发布 `visualViewport.height` 和 `offsetTop`，键盘打开时把应用挂载盒固定到该盒子。本次未采用：WebKit 平移视觉视口时它会跟着移动，会改变 `sidebar-drawer.e2e.ts` 为模拟键盘固定的布局高度，也会让挂到 body 的浮层落在另一套坐标系里。它仍是 WebKit 的唯一路径，所以下面记录的差距是明确决定，而非遗漏。
- **`interactive-widget=overlays-content` 加 `env(keyboard-inset-*)`。** 未采用：它放弃所有缩放，然后要输入框底部、对话内边距和每个固定浮层各自减去键盘高度。它只在 Chromium 生效，代码量也大于它换来的行为。
- **布局高度不变、用键盘 inset 抬高输入框。** 未采用：座位是滚动区内的 sticky 元素，单独抬起会把它画在没有预留空白的对话行之上，而滚动范围的末端仍留在键盘后面。缩小布局视口能直接用输入框自己的底部得到同样的可见结果，无需 transform。
- **键盘缩短滚动区之后跟随底部。** 未采用：那会把对话按键盘高度整体滚上去，读者一点开草稿，正在看的文字就跳走。键盘改变的是输入框的位置，不是读者的阅读位置。

## Consequences

- 在 Android Chromium 上，输入框、草稿和发送按钮停在键盘上沿之上，无需页面平移；对话保持键盘弹出那一刻的屏幕位置，输入框下方的行留在键盘后面，直到读者滚动或有新输出跟随到底部。
- 原本贴底的读者不再被键盘重新贴底；不是键盘切换的布局缩放（窗口、侧边栏）仍会为拥有底部的读者跟随底部。
- WebKit——iOS Safari、所有 iOS 浏览器以及应用内 WKWebView——忽略该键，保留所报缺陷：视觉视口缩小，Safari 平移以露出光标，输入框仍可能部分或全部落在键盘后面。上面那个跟随视觉视口的方案是补齐这条路径的方向。
- 该声明作用于整个文档，所以键盘弹出时的抽屉、菜单或对话框都按缩短后的视口度量。刻意让某部分留在键盘下方的表面，不能再依赖布局视口保持原高度。
- 验证需要真实的 Android 设备，因为该键是浏览器契约，而没有无头引擎会弹出虚拟键盘。`mobile-keyboard.e2e.ts` 在 390×508 下固定两半行为：输入框整卡落在缩短后的视口内且页面无溢出；预置对话的某一行在缩放前后保持同样的屏幕偏移和滚动位置；而没有输入框焦点时同样的缩放仍会把贴底的读者带到底部。`pwa-manifest.e2e.ts` 固定随构建发布的声明。
